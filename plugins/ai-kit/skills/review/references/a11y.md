Review web accessibility compliance for the focus area. Load an accessibility skill when the session
has one, and the project rules' accessibility conventions when they exist.

<scope>$ARGUMENTS</scope>

## Focus Detection

| Argument | Scope |
|----------|-------|
| `buttons` | Button labels, roles, target size, states |
| `headings` | Heading semantics, hierarchy, navigation order |
| `modals` | Focus trapping, modal attributes, dismiss actions |
| `forms` | Form labels, validation, error announcements, input types |
| `all` or _(empty)_ | **All areas** |

## Process

1. **Get Git diff** — changed web UI files (`.tsx`, `.jsx`, `.html`, `.vue`, styles)
2. **Scan focus area(s)** — using the checks below
3. **Check known findings** — match against `.kit-data/a11y/known-findings.json` (if exists)
4. **Report** — unified findings with severity and fix suggestions
5. **Persist new findings** — same as audit-a11y step 8 (dedup by wcag+file_pattern+code_pattern, auto-assign ID, set `source: "review"`). Create `.kit-data/a11y/known-findings.json` if missing.
6. **Save report file** — write the full JSON output to `.kit-data/a11y/fixes/reviews/review-YYMMDD-HHMM.json` (create directories if missing). Print: `Report saved: .kit-data/a11y/fixes/reviews/review-YYMMDD-HHMM.json`

## Checks

- ARIA attributes, semantic HTML, landmark roles
- Keyboard navigation (`:focus-visible`, tab order, focus trapping in modals)
- Form labels, error announcements, `aria-live` regions
- Color contrast, accessible names on icon buttons, heading hierarchy

## Rules

- Never skip findings — report all issues regardless of severity
- Always suggest concrete fixes, not just problem descriptions
